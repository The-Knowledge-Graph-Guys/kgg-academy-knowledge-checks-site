ABox Workbench

Add the facts: instances typed by your classes, controlled values picked from your taxonomy, questions answered live

  • three layers, three jobs the TBox gives the types, the SKOS taxonomy gives controlled values, the ABox is where the facts go; a concept is a value, never a class
  • Foundation load the module's one .ttl file (ontology, concept schemes, instances) or the ontology and the taxonomy as two files, read-only; a concept named like a class is flagged (Activity 1 happens in the files)
  • Activity 2, Build pick a class, name the instance, fill in its properties: a typed value, a link to another instance, or a controlled value from the taxonomy picker; every fact in words next to its Turtle; domain, range and datatype checked as you type, with the inference a reasoner would draw
  • a live graph of the facts, redrawn with every edit: instances, controlled values, classes and values as nodes, each fact as a labelled edge, a flash on what was just written; the answer graph lights the instances that answer a question and draws the skos:broader climb
  • questions as fill-in-the-blanks which class, and what must be true about it; subclass and skos:broader expansion; live answers and the first statement with no match; a detailed editor for two-hop questions
  • Activity 3 the SPARQL for each question in the deck's style, copied with the whole graph into the SPARQL Playground
  • review coverage per question, model use (classes with instances, properties used, controlled values in use), warrant per instance, findings in plain words with a link to fix each; exports the submission .ttl, the queries .txt, a report and the project
  • everything in the browser, autosaved to the tab; worked example: the module's music events graph with one question left blank to fill in

Two Jobs for SKOS

SKOS labels and notes on your classes; SKOS concepts as controlled values beside them

  • two kinds of SKOS property labels and notes are OWL annotation properties with no domain; broader, narrower, related and the mapping properties have domain and range skos:Concept
  • job one, annotations prefLabel, altLabel, hiddenLabel, definition, scopeNote, example, historyNote and changeNote on a class or a property, one preferred label per language, nothing changes for a reasoner
  • job two, controlled values rdf:type for the class, a property with range skos:Concept for the concept; rdfs:subClassOf propagates types, skos:broader is climbed by a query path
  • one word, two layers when a word earns a class and when a concept; rdfs:seeAlso to link them, never owl:sameAs, skos:exactMatch or rdf:type; punning left for later
  • six checks that keep the layers apart in any file, and which ones the ABox Workbench runs
  • twelve questions with explanations and links back to the section that teaches each one

Modules 1 to 5 explainer

Why the TBox Stays Small

ABox and TBox, class explosion, and why object properties, data properties and subclasses need care

  • the TBox lists kinds of thing, the ABox lists things, the CBox lists allowed values; two questions sort any statement; three layers, three speeds of change
  • class explosion a value in a class name multiplies the TBox by every dimension; an interactive counter for genres, instruments and cities; the adjective test
  • when a subclass is earned a new property or rule, the all-members-always promise, and members that keep landing in two siblings
  • object properties domain and range are inferences, a property per class or per value is the same explosion, sub-properties for real extra meaning, keep the domain as wide as the uses
  • data properties literals end the graph, city as a string versus a node, one property per datatype, no property named after another class, type every literal
  • separation of concerns as three files with three owners; seven mistakes to find in any Turtle file; ten questions with explanations

Modules 3 to 5 explainer

Requires, Two Ways

"An electric guitar requires an amplifier", modelled with SKOS concepts as values and with no SKOS at all

  • the sentence is a rule about every electric guitar and a fact about one guitar; the fact is the same object property in both models
  • with SKOS as values types are concepts, a thing says its type through a property, the rule is an Accessory Requirement individual with two values in the ABox
  • without SKOS types are classes, a thing says its type with rdf:type, the rule is an owl:someValuesFrom restriction on the class in the TBox
  • what a reasoner adds in each model (a property chain; the superclasses) and why neither flags a missing cable under the open world assumption
  • the gap query in both models; eight rows that decide between the models; twelve questions, six of them sorting Turtle into the model it belongs to

Modules 3 to 5 explainer

Instruments in Three Layers

SKOS kinds and accessories, an OWL TBox of musicians and physical instruments, and the facts about one concert: built up until one question needs all three

  • kinds as a SKOS scheme twelve instrument kinds in three branches, labels, definitions, scope notes; a kind is a value, never a class
  • a kind is a concept, the instrument in your hands is an instance: five classes and ten properties, two of them with range skos:Concept (plays, is of kind), the class named Physical instrument on purpose
  • required accessories between kinds ex:requires as a sub-property of skos:related (the ISO 25964 way to add a relationship type), the symmetric inference, the S27 rule, inheritance through skos:broader* in the query
  • the ABox three musicians, three physical instruments, three makers, one concert; every line a type, a controlled value, a link or a value
  • one question, three layers the gear-list query line by line, its nine answers, and two more queries; the whole graph as a downloadable Turtle file for the Workbench, the Practice Room and the Playground
  • where everything in the music world goes a decision table from Bass guitar to Höfner to Rock to a music lesson
  • the same word in three layers labels may repeat, IRIs must differ; a namespace per layer, a naming convention, different labels, or punning (not in this course); the ex:musician clash between this file and the Module 5 graph
  • fourteen questions with explanations and links back to the section that teaches each one
